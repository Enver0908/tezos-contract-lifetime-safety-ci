# Measurement contract

The MVP reports the minimum positive integer gas budget at which one Michelson script execution succeeds under a pinned Octez mockup protocol. The budget search does not call the runner with zero gas. At a measured minimum of one, no result is reported for an unobserved zero-gas call.

The result is not exact consumed gas, an operation-wide cost, storage burn, or a guarantee that internal operations will succeed. `run_code` returns final storage, generated internal operations, lazy-storage diffs, and emitted events; the MVP does not execute generated internal operations. Event records are separated from internal operations because Octez can serialize `EMIT` records in the RPC `operations` array with `kind: event`.

The search distinguishes a declared budget exhaustion from `script_rejected`, type errors, malformed output, timeout, and Docker/runtime failure. Only a structured gas-exhaustion result is allowed to move the lower bound of the integer search. A `FAILWITH` message that happens to contain the word “gas” remains a script rejection.

Each result has a `cap_kind`: `policy` for legacy manifest-v1 search caps, `search` for an explicitly declared schema-v2 measurement search cap, and `protocol` when the search ceiling equals the pinned protocol hard limit. The v2 corpus uses the protocol hard limit as its search ceiling. The separate `policies/growth-signal-20000.json` profile is applied offline to a completed report; its 20,000 minimum-successful-budget threshold is a project signal, not a protocol limit and not the measurement search ceiling. A protocol-cap failure applies only to the measured single-script mockup call; it is not an operation-wide or mainnet incident claim.

For a successful result, the runner checks that the storage, emitted operations and lazy-storage diff at the measured minimum match the same fields at the selected cap. If the sampled successful budgets produce different semantics, the measurement is invalid (`budget_dependent`). At minimum budget one, the report records no failed lower boundary.

Schema-v1 input storage is generated independently for every size. Schema-v2 cases are explicit, hashed storage/input/context files. Directly supplied states are labeled `constructed_state`. `single_script_sequence_validated` is reserved for the TzSafe signature snapshots, whose states are derived by feeding each successful pinned-mockup `run_code` storage/lazy-storage result into the next `create_proposal`/`sign_proposal` call. The trace records each call and the corresponding fixture hashes. It validates only that tested single-script sequence; it does not establish full-chain reachability or apply internal operations. Big-map entries are supplied through the protocol's lazy-storage context mechanism where required; they are not converted into an ordinary list to manufacture a warning.

Schema-v1 manifests retain the `integer_budget_search_v2` method. Explicit schema-v2 manifests use `integer_budget_search_v3`, include ordered complete-coverage metadata, and require exactly two identical measurement passes. Each v2 successful measurement stores the semantic output and its hash, plus input bytes, context hash, state-validity label, and sequence-trace hash where applicable. Schema-v3 reports preserve both legacy and explicit-case provenance; schema-v3 baselines are required for schema-v2 experiments. Report and baseline writers refuse to overwrite existing artifacts. `tlsci evaluate` can apply a policy to a completed schema-v3 report without rerunning Octez, after checking the measurement checksum and complete case coverage.

The result is valid only when code hash, fixture hash, context, protocol, Octez digest, cap kind and measurement method are present in the report.

The separately versioned `bounded-sequence-v1` experiment uses `size` as the number of completed calls, not as pre-call storage cardinality. It begins at empty storage, feeds all 4,096 successful `run_code` storage outputs into the next invocation, and records storage cardinality independently at its nine fixed checkpoints. Its post-saturation comparison is limited to the five predeclared checkpoints after 64 calls and requires exact equality of minimum successful integer gas budgets under the same script, `Unit` input, context, protocol, and Octez image. This condition is an experiment-specific consequence to test; it is not a protocol-wide bounded-cost guarantee. Its trace validation and direct gas-boundary replays are implemented in `tools/bounded_sequence.py` and `tools/verify_technical_go_v3.py`.
